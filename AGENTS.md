# AGENTS.md — JM ProjectOP

Инструкции для AI-агентов, автоматизированных разработчиков и участников проекта. Действуют для **всего репозитория**, пока не переопределены более локальными инструкциями.

## 1. Миссия и границы

JM ProjectOP — планируемая **local-first утилита автогеймплея и управляемого монтажа** для onboard/paywall на ассетах Phone Case. Главный результат — **редактируемый проект**, из которого генерируется MP4. V1 поддерживает **только Phone Case** и согласованные механики clean → draw → stickers → reveal. Не превращайте V1 в универсальную игровую платформу, облачный сервис или AI-видеоредактор.

**Перед началом любой разработки прочитать в порядке приоритета:**

1. [docs/PRODUCT_SPEC.md](docs/PRODUCT_SPEC.md) — пользовательские требования и критерии приёмки.
2. [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) — предлагаемая архитектура и интерфейсы.
3. [docs/ROADMAP.md](docs/ROADMAP.md) — порядок поставки.
4. [docs/decisions/ADR-0001-foundation-proposal.md](docs/decisions/ADR-0001-foundation-proposal.md) — предварительные технологии и вопросы для утверждения.
5. [LICENSE](LICENSE), [SECURITY.md](SECURITY.md) — права и безопасность.

При конфликте не подменять продуктовые требования предположением. Зафиксировать расхождение и предложить ADR.

## 2. Основные архитектурные правила (MUST)

1. **Проект > исходные дубли > монтажный план > экспорт.** MP4 — производный артефакт и никогда не заменяет редактируемый ProjectDocument.
2. **События генерируются игрой как доменные данные.** Не пытаться определять смысл очистки/рисования только анализом пикселей видео.
3. **Детерминированное выполнение.** Все случайные решения имеют seed. Simulation использует фиксированный tick; доменная логика не опирается на wall-clock time, requestAnimationFrame или UI timing.
4. **Единый timebase.** Разделять simulation tick, source/capture frame и edit timeline frame. Все границы клипов считать целыми кадрами; финальный target — 30 FPS.
5. **Чистый Domain.** Бизнес-модель и валидаторы не импортируют React, движок графики, FFmpeg, FS или сетевые API.
6. **Явные интерфейсы модулей.** UI → Application → Domain. Адаптеры реализуют порты. Модули не лезут друг другу во внутренние файлы.
7. **Phone Case изолирован.** Конкретные stage/mechanics/action implementations не должны проникать в монтаж, сохранение или экспорт.
8. **Версионируемые контракты.** JSON-структуры (PlanIR, GameEvent, CaptureTake, ProjectDocument, EDL, JobSpec) имеют schemaVersion и runtime validation; несовместимые изменения требуют миграции.
9. **Адресная инвалидация.** Изменение ассета/состояния должно отметить affected stages через граф зависимостей; запрещено тихо оставлять stale clips или выдавать их за готовый материал.
10. **Стабильные ID.** Project, scene, stage, action, event, asset, take, clip, job идентифицируются однозначно. Пути/индексы массива не служат идентичностью.
11. **Предпросмотр и финальный кадр используют общий scene evaluation/render contract.** Нельзя писать «отдельную похожую» логику предпросмотра, которая расходится с MP4.
12. **Validate before execute.** Текст сначала переводится в PlanIR, проверяется и показывается пользователю; неизвестное/несовместимое помечается ошибкой, не исполняется.
13. **Single-machine first.** Модульный монолит, локальные задания, без инфраструктуры микросервисов/авторизации/облака до появления требования.
14. **No secret or unauthorized asset commits.** Не коммитить токены, закрытые игровые материалы, временные видео, кэш и лицензированные ассеты без подтверждённых прав.

## 3. Рекомендации (SHOULD)

- Минимальный сквозной вертикальный срез важнее больших пустых классов и слоёв.
- Новая механика добавляется как StageDefinition с предусловиями, состоянием, действиями и событиями.
- Правила отбора монтажных интервалов находятся отдельно от игры; реализуются test-first на событийных фикстурах.
- Сохранение проекта атомарно, с migration tests, checksum и возможностью relink при потере ассета.
- Ассеты имеют стабильный ID и hash. Cache keys включают зависимости, версии runtime и render preset; кэш полностью пересоздаваем.
- Каждое задание имеет progress, timeout, cancel, status, диагностику и чистую очистку temp-файлов.
- Рендер оценивается покадрово; не предполагать, что browser realtime recording всегда выдаст стабильный output.
- Структурировать PR небольшими задачами, фиксируя объём изменений, тесты и ограничения.
- Новые зависимости устанавливать только при обосновании. Точные версии фиксировать lockfile.
- Документировать публичные контракты, решения в ADR и миграции.
- Использовать понятные точные имена (SceneState, CaptureTake, GameEvent, EditDecisionList), не общие Manager/Helper/Service без ответственности.

## 4. Предлагаемый порядок работы агента

1. Прочитать требования и соответствующие разделы архитектуры; проверить текущую ветку и состояние репозитория.
2. Назвать затронутые модули, данные, зависимости и риски.
3. Для архитектурных изменений предложить/добавить **ADR**, описать альтернативы и последствия. Если стек не утверждён, не объявлять его принятой нормой.
4. Реализовать **один вертикальный срез** с минимальной конфигурацией, без заглушек «готово».
5. Добавить unit + integration tests по инвариантам, обновить документацию только если контракт/поведение изменились.
6. Проверить нормальное выполнение, ошибки и возможность повторного рендера для затронутого сценария.
7. Сообщить точно: что реально работает, что в планах, что не проверено. Не заявлять о тестах, если они не запускались.

**Git workflow:** для объёмных задач отдельная ветка с PR; не переписывать историю main и не удалять рабочий код без явного задания. Пользовательский код и изменения других людей не затирать. Ветки docs/ для документации, feat/ для функций, fix/ для исправлений.

## 5. Требования к готовности изменений

Код/фича считается готовой только при наличии:
- реализованного поведения, а не макета интерфейса;
- runtime validation входных данных и осмысленных ошибок;
- теста нормального сценария и хотя бы одного характерного отказа;
- подтверждения, что повторяемость и таймкоды не нарушены;
- корректной адресной инвалидации при изменениях;
- обновления версий контракта и миграций, если формат менялся.

**Системная приёмка V1:** все критерии раздела 8 PRODUCT_SPEC.md, включая замены рисунка/наклеек после монтажа, оба safe-zone preset, трёхкратный loop и MP4 H.264 30 FPS.

## 6. Чего не делать

- Не кодировать монтаж как набор произвольных timestamp-вырезок без связи с game events и состоянием.
- Не хранить редактируемость только в готовом mp4 или screenshots.
- Не выполнять без проверки произвольный JSON/JS из текстовой инструкции/LLM.
- Не смешивать графическую сцену и бизнес-логику этапов.
- Не расширять MVP на другие игры, cloud render, генеративное видео, «универсальный AI», если задача не поставлена.
- Не выдавать неподтверждённые права на сторонние ассеты и фирменные знаки.
- Не принимать красивый README или skeleton за работающее приложение.
