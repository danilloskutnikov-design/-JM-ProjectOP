## 1. Цель архитектуры

Сделать **local-first** инструмент, который (1) воспроизводит сценарий Phone Case, (2) сохраняет состояние, действия, события и видеоматериал, (3) строит редактируемую монтажную последовательность, (4) перегенерирует только зависимые сцены после изменений и (5) экспортирует H.264 MP4 / 30 FPS в пресетах Onboard и Paywall.

**Архитектурный инвариант №1: проект — источник истины, экспорт — производный артефакт.** Нельзя проектировать монтаж как необратимое редактирование единственного MP4.

**Инвариант №2: логика игры, принятие монтажных решений, графический рендер и кодирование видео независимы друг от друга через явные контракты.**

**Инвариант №3: проектирование для расширения ≠ разработка универсального редактора в V1.** Первый сценарий — только согласованные механики Phone Case. Платформенные интерфейсы существуют там, где нужны для V1, без преждевременной инфраструктуры плагинов, облака, микросервисов или машинного зрения.

## 2. Выбранная структурная форма

**Рекомендуется модульный монолит**, запуск на одной рабочей станции, без сервера и облачной инфраструктуры. Внутри — строгая слоистость:

1. **UI / Presentation**: редактор ассетов и сцены, составитель сценария, предпросмотр, timeline, очередь задач. Не знает, как устроено кодирование видео.
2. **Application / Use cases**: команды и оркестрация: ValidatePlan, RunTake, ComposeTimeline, ReplaceAsset, RebuildAffected, ExportVideo, BatchExport, Save/OpenProject.
3. **Domain / Contracts**: чистые типы, схемы и правила: сцены, действия, события, монтаж, зависимости, сейвзоны, валидация. Не имеет зависимостей от UI, FFmpeg, файловой системы или графического движка.
4. **Modules / Adapters**: Phone Case, графика, фиксация кадров, хранилище проектов, файловые операции, видеоэнкодер, необязательный текстовый парсер.
5. **Job runner**: ограниченная локальная очередь с отменой, тайм-аутом, прогрессом и протоколом ошибок.

~~~mermaid
flowchart TD
    UI[UI: Assets / Scenario / Timeline / Preview] --> APP[Application: commands and orchestration]
    APP --> CORE[Domain + versioned contracts]
    APP --> PLAN[Scenario planner + validator]
    APP --> RUN[Phone Case deterministic runtime]
    RUN --> EVENTS[Actions + event log + snapshots]
    RUN --> FRAMES[Frame renderer / capture]
    EVENTS --> EDIT[Event-based clip selector]
    FRAMES --> EDIT
    EDIT --> TIMELINE[Editable timeline + dependency graph]
    TIMELINE --> PROJECT[Project store + cache]
    APP --> PROJECT
    TIMELINE --> RENDER[Timeline renderer]
    RENDER --> ENCODER[Local H.264 MP4 encoder]
    APP --> JOBS[Queue + progress + error handling]
    JOBS --> RUN
    JOBS --> RENDER
~~~

Модули в схеме — **логические границы**, а не обязательные отдельные процессы.

### Направление зависимостей

- UI → Application → Domain.
- Infrastructure/Adapters реализуют интерфейсы Domain/Application, но Domain никогда их не импортирует.
- Phone Case реализует интерфейс игры/этапов; монтаж не импортирует внутренности Phone Case.
- Editor не управляет покадровым игровым состоянием напрямую; только отправляет команды и показывает сформированные view models.
- Внешние библиотеки используются через тонкие адаптеры, чтобы не связывать формат проекта с конкретным UI/движком/кодеком.

## 3. Предлагаемая структура исходников

Это **целевой ориентир, а не уже существующие каталоги**. На первом вертикальном срезе модули можно держать внутри одного пакета, выделяя пакеты только при реальной необходимости.

~~~text
src/

  domain/               # чистые сущности, инварианты, версии схем
    contracts/
    models/
    rules/
  application/          # use cases / порты / команда-обработчики
  modules/
    assets/             # catalog, stable IDs, metadata, hashes
    scenario/           # parsing → PlanIR → validation
    gameplay/
      phone-case/       # mechanics, state, actions, bot, stages
    capture/            # takes, snapshots, events, frame providers
    editing/            # event rules, shot selector, timeline
    projects/           # loading, saving, migrations, dependency graph
    rendering/          # deterministic scene/frame generation
    export/             # MP4 encoding, presets, loop checks
    jobs/               # queue, cancel, retries, progress
  adapters/             # filesystem, encoding, graphics, text parser
  ui/                   # screens, controls, view models
tests/
  unit/
  integration/
  golden/
  fixtures/
docs/
  ARCHITECTURE.md
  PRODUCT_SPEC.md
  decisions/
~~~

**Запрет**: не создавать много npm-пакетов, микросервисов или «универсальный движок» до подтверждения реальной потребности. Сохранять логические границы, даже если всё компилируется одним приложением.

## 4. Подсистемы и зоны ответственности

| Подсистема | Отвечает за | Не отвечает за |
| --- | --- | --- |
| Asset Catalog | ID, тип, размеры, версии/хэши, пути, права доступа, совместимость | Игровую анимацию |
| Scenario | UI/текст → PlanIR, проверки, ошибки, preview плана | Произвольное исполнение пользовательского текста |
| Phone Case | Машина состояний, механики, детерминированный бот | Нарезку и MP4 |
| Capture | Дубль, кадры/источники кадров, журналы действий/событий, snapshots | Выбор лучших эпизодов |
| Montage | Правила видимости, отбор полезных интервалов, монтажный план | Изменение мира Phone Case |
| Project | Сериализация, миграции, ресурсы, зависимости, кэш | Игровую логику |
| Rendering | Сборка кадра по проекту/таймлайну/пресету | Решение, какой эпизод нужен |
| Export | Параметры H.264/MP4, контроль FPS/размера, запись файла | Содержимое сценария |
| Jobs | Восстановимые задания, прогресс, тайм-аут, отмена | Смысл монтажных правил |

Каждая подсистема должна иметь один публичный фасад, хотя внутри может содержать несколько компонентов. Вызовы соседних модулей идут через фасады/контракты, а не через доступ к внутренним файлам.

## 5. Канонические сущности и контракты

**Все долговременно сохраняемые структуры версионируются** и валидируются при загрузке. Ниже — минимальные предложенные имена и содержание, а не окончательные TypeScript-типы.

| Сущность | Существенные поля |
| --- | --- |
| **AssetRef** | assetId, role (background/case/drawing/sticker/tool), uri, hash, metadata, license/source |
| **SceneState** | gameId, sceneId, caseId, backgroundId, objects (positions/colors/scale/visibility), progress, stage state |
| **ActionSpec** | actionId, stageId, type, input, target, speed, constraints |
| **PlanIR** | schemaVersion, ordered stages, actions, durations, output settings, warnings/errors |
| **RunConfig** | planId, initialStateRef, assetManifestHash, deterministicSeed, runtimeVersion, fixedTickRate |
| **CaptureTake** | takeId, RunConfig, captured frames/clip references, action log, event log, key snapshots, status/error |
| **GameEvent** | eventId, type, takeId, stageId, actionId?, simTick, payload, schemaVersion |
| **TimelineClip** | clipId, takeId, [inFrame,outFrame), targetDurationFrames, source dependencies, overrides |
| **EditDecisionList** | ordered clips, transitions, loop strategy, output preset |
| **ProjectDocument** | schemaVersion, projectId, asset manifest, plan, scenes, takes, timeline, render settings |
| **RenderJob** | id, project revision, render spec, status, progress, output, diagnostics |

### Пример интероперабельного события

~~~json
{
  "schemaVersion": 1,
  "eventId": "evt-000108",
  "type": "visual.change",
  "takeId": "take-001",
  "stageId": "clean",
  "actionId": "clean-stroke-01",
  "simTick": 240,
  "payload": {
    "change": "dirt_removed",
    "progressBefore": 0.25,
    "progressAfter": 0.42
  }
}
~~~

Правила: время как **целочисленный тик**, а не накопленная дробная длительность; изменения состояния доступны независимо от визуализации; тип события и payload проверяются валидатором; не распознанный тип не должен незаметно портить монтаж. У событий устойчивые ID в рамках дубля.

### Пример PlanIR

~~~json
{
  "schemaVersion": 1,
  "gameId": "phone-case",
  "seed": 12345,
  "stages": [
    {"id": "clean", "durationFrames": 90, "action": "clean"},
    {"id": "draw", "durationFrames": 120, "action": "draw", "assetId": "drawing-flower"},
    {"id": "stickers", "durationFrames": 90, "action": "place_stickers", "assetIds": ["sticker-01"]},
    {"id": "reveal", "durationFrames": 60, "action": "show_result"}
  ]
}
~~~

Этот JSON — **пример целевого представления**, не загружаемый сегодня файл. Все диапазоны, поля, несовместимости и значения по умолчанию будут оформлены отдельными схемами и тестами на этапе реализации.

## 6. Подсистема Phone Case: данные прежде картинки

Логика игры строится вокруг **SceneState + ActionSpec → SceneState' + GameEvents**. Рисование, очистка и установка наклеек реализуются как действия, влияющие на состояние. Визуальные переходы — детерминированные проекции состояния на шкалу времени, а не единственный источник информации о том, «что произошло».

Предложение по stages:

1. **CleanStage**: загрязнение, маска очистки, движение инструмента, процент удалённого загрязнения; полезное событие — видимое уменьшение загрязнения.
2. **DrawStage**: выбранный рисунок, траектория/маска проявления, цвет, прогресс раскрытия; событие — появление нового содержимого.
3. **StickerStage**: идентификаторы наклеек, размещение, масштаб, закрепление; событие — появление и фиксация наклейки.
4. **RevealStage**: камера, инструменты вне видимой области чехла, финальное положение и экспозиция результата; событие — result.ready.

**Сохранение результата каждого действия обязательно**: выходное состояние CleanStage становится входом DrawStage и т. д. Порядок этапов настраивается **только при прохождении проверки допустимости**: нельзя требовать рисование на несуществующей поверхности или показывать неготовый чехол как завершённый.

Будущие механики добавляются через регистрацию StageDefinition, содержащего ID, входные требования, выходное состояние, доступные действия, типы событий, зависимость от ассетов и монтажные маркеры. В V1 регистрируются только четыре поддерживаемых этапа.

**Бот** выдаёт доменные действия («провести очистку по кривой», «разместить наклейку»), а не последовательности случайных экранных кликов. UI может показывать те же действия через анимацию курсора или инструмента.

## 7. Детерминизм и общая шкала времени

Для первого прототипа рекомендуются:

- **фиксированный simulation tick**, первоначально 60 ticks/second;
- **выходной 30 FPS** как источник монтажных frame indices;
- **заданный seed** для всего случайного: выбор вариации траекторий, параметров анимации и т. д.;
- **виртуальное время** во всех игровых/монтажных вычислениях (без Date.now и requestAnimationFrame в доменной логике);
- сохранённые версии runtime, ассетов, начального состояния, планов и action log.

**Важно различать:** симуляционный тик, кадр исходного дубля и кадр финального таймлайна. Преобразование между ними выполняет один Timebase-модуль. Для 60/30: outputFrame = simTick / 2 в точках выборки, с явными правилами для событий между соседними кадрами. Не производить монтаж арифметикой floating point секунд.

Предпочтительная модель захвата — **offline frame stepping**: движок получает конкретный simTick и отдаёт соответствующий кадр; это стабильнее записи реального времени для переиспользуемой автоматизации. Видео/превью из тех же кадров/состояний должны быть согласованы. При необходимости потоковая запись — отдельный адаптер, не влияющий на игровой контракт.

Реплей считается корректным при совпадении семантических событий и состояний; бинарно одинаковые пиксели на разных GPU/платформах не гарантируются автоматически. Допуски визуального сравнения фиксируются тестами.

## 8. Захват дублей и типизированные события

Единица исходного материала — **CaptureTake**: запуск сценария или этапа со всеми воспроизводимыми метаданными. CaptureService сохраняет:

- стартовый snapshot и ссылку на хэши зависимостей;
- seed, версию runtime, tick rate;
- упорядоченные ActionSpec/ActionLog;
- типизированные GameEvents и ключевые snapshots;
- диапазоны доступных frames / временный видеоматериал;
- исходный/конечный state hash, status и diagnostics.

События как минимум: stage.started, action.started, action.progress (при значимом изменении), visual.change, action.completed, stage.completed, result.ready и capture.failed. При необходимости вводится stage.aborted и capture.timeout. Частоту action.progress ограничивать, чтобы журнал не разрастался на каждом тике.

**Согласованность:** событие фиксируется вместе с commit состояния на конкретном симуляционном тике. Сторонние UI-таймеры не используются в качестве монтажных таймкодов.

**Защита от зависания:** у стадии есть допустимый диапазон тиков и предел отсутствия прогресса. По превышении выдавать типизированную ошибку и завершать дубль; автоматический retry — ограниченный и диагностируемый.

## 9. Автомонтаж и монтажный документ

Монтаж строится в два шага:

1. **Selection:** правила этапа находят интервалы исходных дублей по events + state progress: начало → значимое действие → завершение/результат. Каждый выбранный интервал получает machine-readable причину выбора и метрику качества. Ожидание/загрузка/бесполезные движения удаляются или ускоряются.
2. **Composition:** алгоритм размещает интервалы на edit timeline, выполняет допустимый trim/retime, переходы и правила продолжительности. Итог хранится как независимая **EditDecisionList** — не склеенный файл.

Пример полезного фрагмента CleanStage: переход от 20% к 60% чистой поверхности в достаточно крупном плане, а не пауза перед началом действия. Стратегии отбора отдельны от Phone Case: игра сообщает «что произошло», монтаж решает «что показывать».

**Недостаток материала:** если порог качества/требуемое событие не выполнен, Montage возвращает MissingCoverage со stageId, критериями и причиной. Оркестратор может заказать новый CaptureTake только для нужных зависимостей либо показать корректируемую ошибку. Не генерировать произвольный контент для сокрытия пробелов.

**Ручные правки:** сцены и таймлайн сохраняют стабильные IDs; изменения порядка, длительности, выбранного дубля и перехода — отдельные команды с undo/redo. Повторная автоматическая сборка должна учитывать пометки ручной фиксации (locked edits), а не стирать решение пользователя.

## 10. Изменение ассетов и адресная перегенерация

Система хранит **граф зависимостей**: asset/config/state/action → stage capture → timeline clip → final render. Узлы содержат версию алгоритма и content hash; изменение параметра инвалидацирует только транзитивно зависимые узлы.

Примеры:

| Правка | Минимальная ожидаемая реакция |
| --- | --- |
| Фон сцены | Перерендерить видимые сегменты затронутых сцен без изменения edit decisions |
| Рисунок | Повторно исполнить/рендерить рисование; проверить зависимость наклеек и пересобрать финал |
| Наклейки | Перегенерировать размещение и финальную демонстрацию; не трогать завершённую очистку |
| Длительность клипа | Пересобрать timeline/render; не переснимать игру, если исходных кадров хватает |
| Цвет/масштаб чехла | Перерендерить сцены, использующие изменённое состояние; перепроверить safe zones |
| Output preset | Перерендерить выход/композицию и safe-zone проверки; не изменять gameplay |

Если правка нарушает предпосылки действия (например, траектория заходит за новый чехол), пометить **needs-recapture** и не выдавать устаревший клип за валидный. Если зависимость сомнительна — выбираем безопасную полную перегенерацию affected stages, не оставляем stale material.

Принципы cache key: (scene state hash, asset hashes, actions hash, runtime version, seed, render profile, renderer version). **Кэш — производный и удаляемый**; проект обязан открываться и восстанавливаться без старого кэша.

## 11. Проект, сохранение и переносимость

Предлагаемый первичный формат — **директория проекта** с открытым версионированным манифестом. Это проще отлаживать, мигрировать и восстанавливать, чем один монолитный видеофайл. Возможность упаковать директорию в переносимый архив — отдельный этап.

~~~text
example.jmproj/
  manifest.json             # schemaVersion, projectId, gameId, revision
  assets/                   # только разрешённые встроенные ассеты (optional)
  refs.json                 # assetRef, URI, sha256, origin, license
  scenario.json             # validated PlanIR + editable source instruction
  scenes.json               # initial and edited SceneStates
  takes/                    # take metadata, actions, events, snapshots
  edit/timeline.json        # EDL, trims, transitions, locks
  outputs/                  # экспорт, НЕ источник истины
  cache/                    # удаляемое производное содержимое
~~~

Схема примерная, допускает уточнение ADR и миграциями. Внешние большие файлы хранить ссылками с hash/version; переносимый пакет должен уметь включать лицензируемые файлы **только при наличии прав**. При отсутствии ассета открывать проект с явной диагностикой и мастером relink, не подменять его тихо.

Сохранение **атомарное** (temp file + rename), с запасной копией и проверкой целостности; schemaVersion обязателен; открытие старых проектов — через явные миграции с тестовыми фикстурами. Запрещены абсолютные пользовательские пути как единственный способ ссылки; пути канонизируются, защита от path traversal обязательна.

## 12. Форматы, композиция и сейвзоны

**Onboard:** 1124×1124, safeRect x = [150,974], y = [150,974], размер 824×824.

**Paywall:** 1124×1000, safeRect x = [200,924], y = [185,815], размер 724×630.

Ввести независимые системы координат:

1. Scene space (нормализованная рабочая плоскость: позиция чехла, следы инструментов, наклейки).
2. Output frame space (пиксели выбранного пресета).
3. UI viewport (экран предпросмотра с масштабированием).

Преобразование Scene → Output выполняет **один Camera/Layout Transform**, поддерживающий fit/zoom/offset. Безопасная область проверяется **после** трансформации, на фактических bounds значимых объектов во всём диапазоне нужных кадров, а не только на статичном финальном кадре. Включать bounds инструмента, чехла и важного результата, учитывать поворот/масштаб.

Для другого разрешения safeRect пересчитывается по коэффициентам sx = W / Wbase и sy = H / Hbase. Направляющие UI — overlay предпросмотра и **не кодируются** в MP4.

**Paywall close button:** отдельная конфигурация exclusionRect / overlay preview, задаваемая интегратором. Место и размер крестика не выдумываются автоматически; редактирование фона и композиции позволяет обеспечить визуально спокойную зону.

## 13. Рендеринг, циклы и экспорт

Процесс экспортирования:

1. Validate(ProjectDocument, asset hashes, plan, EDL, preset, safe zones).
2. Resolve dependencies → rebuild only invalid stages.
3. Evaluate timeline at integer outputFrame 0..N−1.
4. Render composition with the same scene renderer as preview, separate deterministic output adapter.
5. Encode H.264 in MP4 at 30 FPS; проверить duration, dimensions, frame count и наличие кадров.
6. Report reproducible job manifest + diagnostics.

**Cut loop**: фиксированный конец и начало без пустых кадров; жёсткий стык допустим по замыслу, а недопустимая «чёрная дырка» — нет.

**Smooth loop**: при необходимости создать дополнительное связующее движение/переход и обеспечить визуально совместимое состояние на границе последнего/первого кадра. Если автоматическое сглаживание ухудшает кадр, показывать ошибку/предпросмотр, не маркировать цикл как «бесшовный» без проверки.

**Тест цикла:** конкатенировать три повтора, обнаружить чёрные/пустые кадры и визуальные скачки вне допуска выбранного режима. MP4 обязан совпадать с предпросмотром по расположению, содержанию и монтажным frame positions; визуальные отличия кодека в пределах тестовых допусков.

## 14. Очередь задач и стабильность

JobRunner — одна локальная очередь с конфигурируемой параллельностью и CPU/GPU budget. Состояния: queued → running → completed / failed / cancelled. Поддерживать progress %, stageId, currentFrame, structured error, logs.

- Каждая операция имеет input fingerprint и может быть перезапущена после сбоя (idempotent outputs / safe temp paths).
- Ошибки делятся на **InvalidPlan**, **MissingAsset**, **IncompatibleAsset**, **Timeout**, **RenderFailure**, **EncodeFailure**, **ProjectMigrationFailure**.
- Retry только для временных сбоев, с лимитом; ошибки валидации не ретраить бессмысленно.
- Отмена убирает незавершённые временные файлы, но не портит сохранённый проект.
- Batch variation = базовый проект + список явных overrides; итог каждого варианта отслеживается независимо, без размножения исходников.

## 15. Сценарий: текст → проверяемое представление

Приоритет — **строгая каноническая форма PlanIR**. UI-конструктор пишет PlanIR непосредственно. Текстовая инструкция проходит отдельный адаптер:

~~~text
User text → parser (deterministic / optional AI adapter)
          → candidate PlanIR
          → schema validation
          → game capability + prerequisite validation
          → user-visible plan / warnings / errors
          → explicitly confirmed executable plan
~~~

Не отдавать сырой текст напрямую игровому движку и не выполнять произвольный код, предложенный языковой моделью. Для MVP хватает ограниченного набора команд; внешний AI-парсер возможен только как заменяемый адаптер, с проверкой результата теми же правилами.

Неизвестные этапы, конфликтующие длительности, недоступные ассеты и нарушенные предусловия отмечаются, а не «исправляются» скрытно.

## 16. UI: важные экраны и принципы

Один рабочий экран с четырьмя зонами: **Asset Library**, **Scene Preview**, **Scenario/Properties**, **Timeline/Jobs**. Порядок этапов и длительности редактируются без обращения к сырому JSON. Пользователь видит:

- режим Run / Preview / Edit / Export;
- текущую revision проекта и dirty-state;
- найденные ошибки плана, источники недостающих ассетов и неопределённые действия;
- кадры из первичного источника, range handles, флаг locked edits;
- настраиваемый сейвзонный overlay и отдельную зону крестика paywall;
- какие сцены помечены invalidated, почему и сколько новых дублей нужно.

UI никогда не должен выдавать «export ready» при наличии неразрешённых зависимостей и stale clips.

## 17. Безопасность и права

Local-first по умолчанию: исходники, пользовательские ассеты и проекты не загружаются автоматически во внешнюю систему. Не включать стороннюю телеметрию без явного решения. Не хранить токены/ключи в проектных JSON и Git. Перед исполнением читать [../SECURITY.md](../SECURITY.md) и [../LICENSE](../LICENSE).

Ассеты Phone Case и JUSTMOBY используются **только после проверки полномочий**; исходные внешние ассеты не публиковать без разрешения. Парсер текстовых инструкций не имеет доступа к shell или произвольной файловой системе. Обработка медиа и путей должна учитывать недоверенные внешние файлы; если encoder вызывается как subprocess — только через структурированные аргументы, не конкатенацией shell-команд.

## 18. Тестовая стратегия и инварианты качества

**Unit:** state reducer, действие → события, PlanIR validator, stage prerequisites, timebase, safeRect, cache invalidation, EDL assembler, asset hash.

**Integration:** Phone Case четыре этапа, capture → selection → timeline → preview → export, read/write project, schema migration, missing asset, cancellation, re-render after replacement.

**Golden/reference:** исходное/конечное состояние и набор событий при фиксированном seed; ключевые кадры с допусками рендера, не только пиксель-хэши.

**Acceptance end-to-end:**

1. Выполнить clean → draw → stickers → reveal.
2. Сохранить/закрыть/открыть проект, воспроизвести дубль; сравнить действия, state hash и события.
3. Заменить рисунок/наклейки; проверить сохранение EDL и перегенерацию **только затронутых** эпизодов.
4. Проверить оба output preset и bounds значимых объектов, в том числе в движении.
5. Экспортировать MP4 H.264 30 FPS и сравнить с preview.
6. Проверить Cut и Smooth loop на трёх последовательных повторах.
7. При невыполнимом плане/отсутствующем эпизоде проверить **понятную ошибку**.

## 19. План архитектурной реализации по вертикальным срезам

**Slice 0 — Contracts:** утвердить стек и структуру, PlanIR/ActionSpec/GameEvent/ProjectDocument, валидаторы и тесты сериализации. Никакого UI-«большого редактора» до проверенного контракта.

**Slice 1 — Deterministic Phone Case:** один механический этап со стабильным состоянием, событием и покадровым повтором; затем остальные три этапа.

**Slice 2 — EDL:** сохранение событий и дублей; выбор ключевых интервалов, рендер из EDL.

**Slice 3 — Editable project:** стабильные ID, замена ассетов, dependency graph, локальная invalidation и пересборка.

**Slice 4 — Product UI + export:** два пресета, сейвзоны, loop, MP4, batch, тестирование/пакетирование.

После каждого slice должен быть работающий сквозной путь, даже упрощённый. Не имитировать готовность кнопками-заглушками.
