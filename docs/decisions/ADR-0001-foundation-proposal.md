# ADR-0001 — предлагаемая архитектурная основа и стек

- **Status:** Proposed — НЕ принято как окончательное решение.
- **Date:** 2026-10-23
- **Scope:** JM ProjectOP V1 / Phone Case / local-first video tooling.

## Контекст

Требуются детерминированное прохождение игровых действий, событийный монтаж, адресный ререндер после изменения ассетов, два точных формата, MP4 H.264 и редактируемый проект. Необходимо удержать низкую сложность MVP и возможность доращивать продукт без переписывания ядра.

## Рекомендуемые решения

1. **Модульный монолит** (один локальный продукт) с Domain → Application → Adapters и независимым UI.
2. **TypeScript** для приложения, контрактов, игровых правил и логики монтажа — общая типизация между интерфейсом и runtime.
3. **Web-based UI** (первый кандидат: React + Vite) с локальным process/job runner. Упаковку в desktop оболочку выбрать после подтверждения ограничений.
4. **2D renderer**, отделённый интерфейсом (кандидат: PixiJS/WebGL); не допускать прямых вызовов графической библиотеки из Domain.
5. **Offline fixed-step frame render** с виртуальным simulation tick (кандидат: 60 Hz); MP4 как постобработка 30 FPS.
6. **FFmpeg через контролируемый локальный adapter** как кандидат для H.264/MP4; не полагаться только на MediaRecorder в браузере для детерминированного экспорта.
7. **Manifest + отдельные файлы в папке проекта** с версии схем, asset hashes, relative refs, backup/migrations.
8. **Без облака, удалённых LLM и SQL-сервера** в MVP. AI-парсер возможен позднее через интерфейс, если подтверждён конкретный сценарий.

## Альтернативы и компромиссы

| Вариант | Причина не выбирать сейчас | Когда вернуться |
| --- | --- | --- |
| Один большой UI + логика игры + кодирование в компонентах | Нельзя надежно тестировать/рендерить воспроизводимо | Никогда как долгосрочный дизайн |
| Микросервисы + облачные воркеры | Высокая сложность, внешние зависимости, риск для ассетов | Появится требование распределённого batch render |
| Универсальный игровой движок до MVP | Перерасход времени, отсутствуют требования других игр | После второй реальной интеграции |
| Запись игрового экрана в real time как главный источник | Пропуски кадров, зависимость от скорости хоста, трудность повторов | Вспомогательный preview/capture adapter |
| Один редактируемый видеоклип без scene state | Невозможна замена рисунка/наклеек после монтажа | Не соответствует ТЗ |
| Только browser API для MP4/H.264 | Кодеки и совместимость зависят от среды | При строгой поддерживаемой платформе и тестах |
| Сразу Electron/Tauri как необратимая платформа | Решение должно учитывать упаковку FFmpeg, безопасность и ОС | После минимального proof-of-concept |

## Что проверить до окончательного выбора

- Целевые ОС и способ запуска (Windows прежде всего? требуется ли веб-браузер без установки?).
- Фактические форматы Phone Case ассетов, используемые эффекты/шейдеры и права на них.
- Проверка реального pixel/frame export: 1124×1124 и 1124×1000 @30 FPS, H.264, отсутствие тёмных/пропущенных кадров.
- Бюджет времени и памяти при 30 FPS, batch + повторный рендер.
- Доступность/распространение FFmpeg и юридические требования к сборке и используемым кодекам.
- Переносимость проекта между машинами и права на bundled assets.
- Реальная необходимость текстового AI-интерпретатора vs строгий простой парсер.
- Одинаковые state/event traces при replay на целевой ОС.
